安全与最佳实践

GitHub 账号往往绑定了你的代码、邮箱、甚至公司仓库。花十分钟把下面几件事做对，能避免绝大多数"账号被盗 / 密钥泄露"事故。

账号安全

  • 开启双重验证（2FA）：优先使用验证器 App 或 Passkey，短信验证码容易被拦截。
  • 保存恢复码：离线存放，不要只存在手机相册。
  • 使用密码管理器：为 GitHub 设置独立强密码，不复用。
  • 定期查看 Active sessions：发现陌生设备立即撤销并改密码。
  • 警惕钓鱼：GitHub 不会通过邮件索要密码或验证码；登录前确认域名是 github.com。

个人访问令牌（PAT）

类型特点建议
Fine-grained token可限定到具体仓库、具体权限，支持过期时间优先使用，只给需要的仓库与读写范围
Classic token按 scope 授权，一次覆盖账号下所有仓库仅在工具不支持细粒度令牌时使用
SSH 密钥无需过期，长期有效长期开发使用，私钥加密码短语
  • 令牌只显示一次，复制后立即存入密码管理器。
  • 设置合理有效期（如 90 天），到期前轮换。
  • 不要在 CI 中把令牌写进代码，使用仓库 Secrets。
  • 不再使用的令牌立刻删除，不要留"备用"。

密钥泄露了怎么办

这是最常见的安全事故：把 .env、云服务密钥、数据库密码提交进了仓库。请按顺序处理：

  1. 第一时间作废密钥：到对应平台（云厂商、数据库、第三方 API）删除或轮换。这是唯一真正有效的止损。
  2. 评估暴露范围：仓库是公开的吗？暴露了多久？有没有被 Fork 或缓存？即使删除提交，历史里仍可能被检索到。
  3. 清理 Git 历史（可选，作废之后再做）： 
    # 使用 git-filter-repo 从全部历史中删除某个文件
git filter-repo --path .env --invert-paths
git push --force --all
git push --force --tags
  4. 通知相关方：公司安全团队、协作成员；必要时联系 GitHub Support 清理缓存。
  5. 加防护：把文件加入 .gitignore，开启 Secret scanning 的 Push protection。
重要

顺序不能反：先作废，再清理。只删文件不换密钥，等同于把钥匙从门上拔下来但没换锁。

Actions 安全

  • 在工作流顶部声明最小权限：permissions: contents: read，需要时再逐项打开。
  • 第三方 Action 固定到完整版本号或提交 SHA，不要用 @master。
  • 不要把密钥传给来自 Fork 的 PR 工作流。
  • 慎用 pull_request_target：它拥有写权限与密钥，若再检出并执行 PR 代码，等于把后门请进门。
  • 优先使用 OIDC 获取云厂商短期凭证，避免长期密钥。

仓库与协作安全

  • 最小权限：给协作者 Read 或 Triage 而不是 Admin；用 Teams 管理权限。
  • 保护默认分支：要求 PR、要求通过检查、要求至少一人批准、禁止强制推送。
  • 启用 Rulesets：可按分支、标签、路径设置更细的规则。
  • 审查大权限应用：定期检查 Settings → Applications 中授权的 OAuth App 与 GitHub App。
  • 私有仓库不等于保险箱：被邀请者、应用、Actions 日志都可能造成外泄。

依赖安全：Dependabot

在仓库 Settings → Code security 中开启：

  • Dependabot alerts：依赖有已知漏洞时通知你。
  • Dependabot security updates：自动创建修复 PR。
  • Dependabot version updates：用 .github/dependabot.yml 定期升级： 
    version: 2
updates:
  - package-ecosystem: "npm"
    directory: "/"
    schedule:
      interval: "weekly"
    open-pull-requests-limit: 5
  • Code scanning：用 CodeQL 扫描注入、越权等代码缺陷，公开仓库免费。
  • Secret scanning + Push protection：提交前拦截密钥，公开仓库默认开启。

开源许可证怎么选

许可证允许要求适合
MIT几乎任何用途保留版权声明希望被广泛使用的小工具、示例项目
Apache-2.0商用、修改、专利授权保留声明、标注修改企业友好、需要专利条款的项目
GPL-3.0商用、修改衍生作品也必须开源希望保证下游持续开源
BSD-3-Clause商用、修改保留声明、不得用作者名义背书偏学术、宽松的场景

没有许可证 = 默认保留所有权利，别人不能合法复制或修改你的代码。想让人用，就明确加上许可证。新建仓库时可以直接选择模板，GitHub 会自动生成 LICENSE 文件。

隐私注意事项

  • 公开仓库中的提交邮箱、时区、活动时间都是公开信息，建议开启邮箱隐私保护。
  • 不要提交真实用户数据、内部文档、包含内网地址的配置文件。
  • 截图前检查是否包含姓名、邮箱、Token、公司内部信息。
  • 使用公司设备与账号时，遵守公司关于代码外发的规定。

常见骗局与风险

  • 假招聘：以"技术测试"为名让你运行陌生仓库的代码。先在隔离环境中审查脚本。
  • 依赖投毒：拼写相似的恶意包（typosquatting），安装前确认包名与来源。
  • 假 Star / 刷量服务：可能导致账号被封禁。
  • "帮我点个 Star"式垃圾 Issue：不要在其中留下邮箱或个人信息。

上手指南之外的检查清单

  • 已开启 2FA，并离线保存恢复码。
  • 使用 fine-grained token 或 SSH，令牌设置了有效期。
  • 公开仓库中没有 .env、密钥、内网地址。
  • main 分支已开启保护，禁止强制推送。
  • Dependabot 与 Secret scanning 已开启。
  • 为项目添加了明确的许可证。
