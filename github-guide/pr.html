Pull Request 协作流程

Pull Request（PR，中文常译为"拉取请求"）是 GitHub 最核心的协作机制：你把自己的分支"申请合并"到目标分支，团队在旁边讨论、评审、跑自动化检查，确认无误后点击合并。

Pull Request 是什么

注意区分两件事：

  • Git 层面：分支合并（git merge），纯本地操作。
  • GitHub 层面：Pull Request，是一个带讨论区的合并申请。代码可以在合并前被逐行评论、被自动测试、被要求修改。

PR 的产物也不只是合并后的代码，还包括一整段可追溯的讨论记录：为什么这么改、评审提了哪些问题、谁批准了。

完整流程一览

  1. 从最新 main 创建功能分支git switch main && git pull && git switch -c feature/xxx
  2. 在分支上提交改动小步提交，说明写清楚"做了什么、为什么"。
  3. 推送到 GitHubgit push -u origin feature/xxx
  4. 发起 Pull Request网页会提示 Compare & pull request，或访问仓库的 Pull requests 标签页。
  5. 写标题与描述说明背景、改动点、如何验证，关联相关 Issue。
  6. 等待检查与评审Actions 自动跑测试；评审人留下评论或要求修改。
  7. 根据意见继续提交在同一个分支上继续 commit & push，PR 会自动更新。
  8. 合并并清理点击 Merge，删除远程分支，本地切回 main 并 pull。

动手发起一个 PR

用命令行推送

git switch main
git pull
git switch -c feature/add-about

# 修改文件……
git add .
git commit -m "feat: 增加关于页面"
git push -u origin feature/add-about

推送后打开仓库主页，通常会看到一条黄色提示条：Compare & pull request。点击它即可进入创建页面。

填写 PR 信息

  • base：要合并进的目标分支（通常是 main）。
  • compare：你的来源分支。
  • 标题：一句话概括，例如 feat: 增加关于页面。
  • 描述：建议包含"改了什么 / 为什么改 / 怎么验证 / 截图"。
  • Reviewers：指定评审人。
  • Assignees / Labels / Projects：负责人、分类标签、关联看板。
## 改动内容
- 新增 about.html 页面
- 导航栏增加"关于"入口

## 为什么
用户反馈找不到团队介绍。

## 如何验证
1. 打开首页，点击导航栏"关于"
2. 确认页面正常显示、移动端布局正常

Closes #12
提示

在描述里写 Closes #12（或 Fixes #12），PR 合并后对应的 Issue 会自动关闭，省去手动操作。

草稿 PR（Draft）

功能还没写完但想先让人看看思路，可以在创建时选择 Create draft pull request。草稿 PR 不能合并，适合早期征求意见；完成后点击 Ready for review 转为正式评审。

代码评审怎么进行

在 PR 的 Files changed 标签页，可以：

  • 把鼠标移到某一行，点击 ＋ 写单行评论。
  • 拖动选择多行，对一段代码评论。
  • 点击 Start a review 把多条评论攒在一起提交，避免反复打扰对方。
  • 用 Suggest changes 直接给出可一键采纳的修改建议。

评审结束时，GitHub 提供三种结论：

结论含义
Comment只留意见，不阻塞合并。
Approve同意合并。分支保护规则可要求"至少 N 个批准"。
Request changes必须先修改并重新评审才能合并。

收到修改意见后

# 还在同一个分支上继续改
git add .
git commit -m "review: 按评审意见调整按钮间距"
git push

不需要新建 PR，也不需要关闭旧的。推送后 PR 会自动更新，评审人可以只查看新增的改动。对每条评论点击 Resolve conversation 表示已处理。

自动检查（Checks）

如果仓库配置了 GitHub Actions，PR 页面底部会显示检查结果。常见状态：

  • ✓ 全部通过 可以合并。
  • ✗ 失败 点 Details 查看日志，修复后重新推送。
  • ● 进行中 等待完成。

分支保护规则可以设置"检查未通过禁止合并"，这是保证 main 始终可用的关键手段。

三种合并方式

方式效果适合
Create a merge commit保留分支上的每一次提交，并额外生成一个合并提交。希望完整保留开发过程
Squash and merge把分支上的所有提交压缩成一次提交，历史干净。分支里有很多"改错字"式的小提交
Rebase and merge把分支提交逐个接到 main 之后，不产生合并提交。追求线性历史

仓库管理员可以在 Settings → General 中只启用其中一种，避免团队风格混乱。

合并之后

git switch main
git pull                 # 把合并结果同步到本地
git branch -d feature/add-about   # 删除本地分支
git push origin --delete feature/add-about  # 如果网页上没删远程分支

GitHub 合并成功后通常会显示 Delete branch 按钮，直接点它即可清理远程分支。

PR 显示有冲突怎么办

说明目标分支在你创建 PR 之后又有了新提交，且改到了同一片区域。两种处理方式：

# 方式一：把 main 的最新改动合进你的分支
git switch feature/add-about
git fetch origin
git merge origin/main
# 解决冲突 → git add → git commit → git push

# 方式二：把自己的提交接到最新 main 之后（仅限个人分支）
git rebase origin/main
git push --force-with-lease

解决后 PR 页面会自动刷新为可合并状态。

协作礼仪

  • PR 要小：改动控制在几百行以内，评审质量会明显提高。
  • 描述要能自解释：不要让评审人靠猜你的意图。
  • 及时响应：收到意见后尽快回复，哪怕只是"今天会改"。
  • 对事不对人：评论针对代码，不针对作者。
  • 不要自己批准自己的 PR：个人项目也建议走一遍流程，养成习惯。
提示

安装了 GitHub CLI 后，可以在终端里直接创建 PR：gh pr create --fill，用提交信息自动填充标题和描述。
