Git 基础命令

日常开发 90% 的操作只涉及七八条命令。这一篇按"看状态 → 看改动 → 提交 → 同步"的顺序讲，并补充出错时如何安全地撤销。

日常循环

git status          # 1. 我现在改了什么？
git diff            # 2. 具体改了哪些行？
git add .           # 3. 把改动放进暂存区
git commit -m "..."  # 4. 记录成一次提交
git push            # 5. 上传到 GitHub
git pull            # 6. 开始工作前，先同步别人的改动

第一步：看清当前状态

git status

最常用、最安全的命令。它会告诉你：当前在哪个分支、哪些文件被修改、哪些已暂存、哪些还没被 Git 跟踪。

$ git status
On branch main
Your branch is up to date with 'origin/main'.

Changes not staged for commit:
  modified:   README.md

Untracked files:
  notes.md

建议在每次 add 和 commit 之前都执行一次，确认没有把不该提交的文件（密码、密钥、临时文件）带进去。

git diff

git diff            # 工作区 vs 暂存区：还没 add 的改动
git diff --staged   # 暂存区 vs 上次提交：已经 add 的改动
git diff 文件名      # 只看某个文件
git diff main..dev  # 两个分支之间的差异

第二步：提交

git add

git add 文件名        # 添加指定文件
git add .            # 添加当前目录所有改动（最常用）
git add src/         # 添加整个目录
git add -p           # 交互式地逐块选择要提交的改动（进阶但好用）

git commit

git commit -m "fix: 修复登录按钮点击无响应"
git commit -am "..."   # 跳过 add，直接提交【已跟踪】文件的改动（新文件无效）

提交说明建议写清"做了什么、为什么"，常见约定是 类型: 描述：

类型用途示例
feat新功能feat: 增加深色模式切换
fix修复 Bugfix: 修复移动端菜单无法关闭
docs文档docs: 补充安装说明
refactor重构（不改变行为）refactor: 拆分搜索逻辑
chore杂项、依赖更新chore: 升级依赖版本
说明

一次提交尽量只做一件事。把"改样式"和"修 Bug"混在一个提交里，将来回退或排查问题会非常困难。提交本身是本地操作，不联网、不花钱，多提交几次没有坏处。

第三步：查看历史

git log                      # 完整历史
git log --oneline            # 一行一条，最常用
git log --oneline --graph --all   # 图形化查看分支
git log -p README.md         # 某个文件的每次改动详情
git log --author="Wang"      # 按作者筛选
git show 提交编号             # 查看某次提交的具体内容
git blame README.md          # 每一行是谁、哪次提交改的

第四步：与远程同步

git remote -v                # 查看远程仓库地址
git fetch                    # 只下载远程更新，不合并
git pull                     # 下载并合并（fetch + merge）
git pull --rebase            # 下载后把自己的提交"接"在最新提交之后，历史更整洁
git push                     # 推送当前分支
git push -u origin 分支名      # 首次推送新分支并建立跟踪
git push --force-with-lease  # 覆盖远程（谨慎，仅在自己独占的分支上用）
注意

养成"先 pull 再 push"的习惯。直接 git push --force 会覆盖别人的提交，在团队共享分支上属于高危操作。

撤销与回退：三种场景

场景 1：改乱了，还没 add

git restore 文件名       # 放弃工作区的改动，恢复到上次提交的状态
git restore .           # 放弃所有未暂存的改动（不可恢复！）

场景 2：add 错了，想撤回暂存

git restore --staged 文件名
# 旧版本 Git 的等价写法：git reset HEAD 文件名

场景 3：提交错了

# A. 只改提交说明（还没推送）
git commit --amend -m "新的说明"

# B. 撤销提交，但保留改动在暂存区
git reset --soft HEAD~1

# C. 撤销提交，保留改动在工作区（默认行为）
git reset HEAD~1

# D. 彻底丢弃这次提交和改动（危险，不可恢复）
git reset --hard HEAD~1
重要

--hard 会永久丢弃未提交的内容，且无法通过普通操作找回。执行前请确认 git status 里没有你还需要的改动；不确定时先 git stash 暂存起来。

已经推送了怎么办

不要用 reset 去改公共历史，而是用 revert 生成一次"反向提交"：

git revert 提交编号
git push

这样历史只增不减，协作者不会被打乱。

临时保存：git stash

手头改到一半，突然要切分支处理别的事，又不想提交半成品：

git stash          # 暂存当前改动
git stash list     # 查看暂存列表
git stash pop      # 恢复最近一次并删除记录
git stash apply    # 恢复但保留记录

.gitignore：哪些文件不该提交

在仓库根目录新建 .gitignore，每行一条规则：

# 依赖目录
node_modules/
vendor/

# 构建产物
dist/
*.log

# 环境变量与密钥
.env
*.pem

# 操作系统文件
.DS_Store
Thumbs.db

已经被跟踪的文件不会被新规则自动忽略，需要先移出索引：

git rm --cached 文件名
重要

密钥一旦被提交进历史，即使后来删除文件，它仍然留在历史记录里可以被翻出来。正确做法是立刻作废该密钥，再清理历史。参见安全与最佳实践。
