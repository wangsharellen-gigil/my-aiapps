分支与合并

分支让多人可以同时改同一个项目而不互相踩脚。理解"分支只是指针"这一点，你会发现它比想象中简单得多。

分支到底是什么

每次提交，Git 都会生成一个内容快照，并记住它的"父提交"。分支本质上就是一个指向某次提交的可移动指针。所以创建分支几乎不占空间，切换也只需瞬间。

A ── B ── C   ← main（主线，指针指向 C）
           \
            D ── E   ← feature/login（从 C 分出来，继续往前走）

默认分支通常叫 main，它代表"当前稳定的、可发布的版本"。新功能在独立分支上开发，完成并评审通过后再合并回 main。

为什么要用分支

  • 隔离风险：新功能写到一半、代码跑不起来，也不会影响 main 上的可用版本。
  • 并行协作：十个人可以同时改十个模块，各自在自己的分支上提交。
  • 方便评审：一个分支对应一个 Pull Request，评审范围清晰。
  • 随时放弃：实验失败，删掉分支即可，main 上什么都没发生。

分支的基本操作

git branch                    # 查看本地分支（* 表示当前分支）
git branch -a                 # 连同远程分支一起查看
git switch -c feature/login   # 新建并切换到 feature/login
git switch main               # 切换到 main
git branch -d feature/login   # 删除已合并的分支
git branch -D 分支名           # 强制删除未合并的分支（确认不要了再用）

# 旧写法（仍可用）：git checkout -b 分支名 / git checkout 分支名

把新分支推到远程，并让之后的 git push 知道推到哪里：

git push -u origin feature/login

-u 是 --set-upstream 的缩写，做一次即可。

合并：把分支合回主线

先切到目标分支（通常是 main），再合并来源分支：

git switch main
git pull                  # 先确保本地 main 是最新的
git merge feature/login

两种情况

快进合并（Fast-forward）

main 在分叉后没有新提交，Git 直接把 main 指针往前移动，不产生新提交，历史是一条直线。

三方合并（3-way merge）

两边都有新提交，Git 会生成一个合并提交，把两条历史连接起来。图形上会出现分叉与汇合。

如果希望每个功能分支都留下合并记录（便于回退整个功能），可以强制生成合并提交：

git merge --no-ff feature/login

解决冲突

当两个分支修改了同一文件的同一片区域时，Git 无法判断该保留哪一个，就会停下来让你决定。

$ git merge feature/login
Auto-merging README.md
CONFLICT (content): Merge conflict in README.md
Automatic merge failed; fix conflicts and then commit the result.

打开冲突文件，会看到这样的标记：

<<<<<<< HEAD
欢迎使用新版登录页面。
=======
欢迎使用全新的登录界面。
>>>>>>> feature/login

<<<<<<< HEAD 到 ======= 之间是当前分支（main）的内容，======= 到 >>>>>>> 之间是来源分支的内容。

处理步骤：

  1. 编辑文件，删掉三行标记，把内容改成你最终想要的样子（可以只保留一边，也可以融合两边）。
  2. 确认没有遗留的 <<<<<<< 标记。
  3. git add 冲突文件 标记为已解决。
  4. git commit 完成合并（Git 会自动生成合并说明）。

想放弃这次合并、回到合并前的状态：

git merge --abort
提示

VS Code、GitHub Desktop 等工具提供可视化的"采用当前 / 采用传入 / 两者都保留"按钮，处理冲突比手改标记更直观。冲突不是错误，只是需要人来判断的业务决策。

rebase：另一种整合方式

rebase 会把你分支上的提交"摘下来"，重新接到目标分支的最新提交之后，历史因此变成一条直线：

git switch feature/login
git fetch origin
git rebase origin/main
注意

不要对已经推送并被别人使用的分支执行 rebase，因为它会改写提交编号，别人的本地历史将无法对应。只在自己独占的功能分支上使用。

团队常用的分支策略

  • 功能分支（Feature branch）：每个需求开一个分支，通过 PR 合回 main。最通用，适合绝大多数团队。
  • 主干开发（Trunk-based）：所有人频繁往 main 提交小改动，配合特性开关。适合自动化测试完善的团队。
  • Git Flow：长期保留 develop、release、hotfix 等多条分支，流程严谨但较重，适合有固定发版周期的项目。

个人学习阶段，用"main + 功能分支 + Pull Request"就足够了。

保护主分支

GitHub 仓库的 Settings → Branches（或 Rules → Rulesets）可以为 main 添加保护规则：

  • 禁止直接推送，必须通过 Pull Request。
  • 合并前必须通过 CI 检查、至少一人评审。
  • 禁止强制推送和删除分支。

这是团队协作的第一道防线，个人项目也建议开启"禁止强制推送"。

动手练习

# 1. 从 main 创建分支
git switch main
git pull
git switch -c feature/hello

# 2. 改点东西并提交
echo "hello from a branch" >> README.md
git add README.md
git commit -m "docs: 在分支上添加一行"

# 3. 推送分支
git push -u origin feature/hello

# 4. 回到 main 合并
git switch main
git merge feature/hello

# 5. 推送并删除已合并的分支
git push
git branch -d feature/hello

在真实协作中，第 4 步通常不是本地合并，而是到 GitHub 上发起 Pull Request——这就是下一篇的内容。
